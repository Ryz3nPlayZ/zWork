# zWork review, 2026-10-31

A pass over the whole repo, the competition, and how students and professionals would actually
get a job done in zWork versus the alternatives. zWork is a product for people who are not
developers (see `POSITIONING.md`); every judgement below is made from that seat.

## 1. Fixed in this pass

Commits `3256395` and `434ef1e` on `site/redesign`.

| Complaint or finding | What was wrong | Fix |
|---|---|---|
| New chat doesn't show in the sidebar until the reply finishes | The sidebar list only refreshed on `done`. The server saves the chat before it sends the `chat` event. | Refresh the list on the `chat` event (`app/src/lib/store.ts`). |
| Leaving a new chat can pull you back to it | A late `chat` event set `activeChatId` unconditionally. | Only swap the id if you are still on that chat. |
| General jank while a reply streams | The offline cache serialised every chat to localStorage on every token. | Write at most once a second. |
| Have to zoom in to read | UI is laid out at 11–13px with no zoom control. | Window opens at 110%, Cmd +/- works (`main.rs`, `tauri.conf.json`). This is a stopgap; see 3.1. |
| Search and sidebar toggle floating oddly in the top bar | Two icons sat 10px below the traffic lights, unrelated to anything. | Toggle sits on the traffic-light row; search moved into the sidebar as "Search chats" (⌘K still works). |
| Projects / Scheduled empty state is a small box at the top | `PageShell` didn't stretch. | Empty states fill the page height with padding; the duplicate header button is hidden while empty. |
| Inbox: two items per scheduled run | The scheduler posted a summary even when the model already called `post_to_inbox`. | No summary if the run already posted. |
| Inbox: summary reads "I'll check your inbox now…" | The summary was the text before the first tool call. | Summary is the text after the last tool call. |
| Inbox: failures show raw errors ("error sending request for url…") | Raw error string posted as the body. | Plain-language reason plus "it will try again at the next scheduled time". Old failures of a task are marked read once it next succeeds. |
| Inbox: Mark read buttons, "Open run" | Opening an item didn't mark it read, so there were extra buttons. "Run" is developer language. | Opening marks it read; button reads "Open conversation". |
| Inbox could leak a verification code | Nothing told the model not to. | `post_to_inbox` description forbids secrets. |
| Inbox items could be lost | Load-modify-save with no lock; a scheduled run posting while you mark items read could drop a change. | One write lock around every inbox write. |

Not checked: zoom level and the toggle's position against the real traffic lights were set
from a measured screenshot, not seen in a built app.

## 2. Problems still open, worst first

1. **Chat store has the same race the inbox had.** `chatstore` does unlocked load-modify-save.
   The title generator (`rename`) runs while the reply is being appended; whichever saves second
   wins, so a reply or a title can vanish. Needs the same lock, but carefully: some chatstore
   functions call each other, so a naive lock deadlocks.
2. **"??????" shows as a model name.** `store.ts:49`, `Onboarding.tsx:265`, `ModelPicker.tsx:196`
   and comments in `api.ts` show `??????` for `zwork-apex`. Looks like a bad find-and-replace in
   `a65a731`. A new user sees this on the first screen.
3. **Inbox flags attach to the wrong task.** `post_to_inbox` looks up the task through
   `last_chat_id`, which the scheduler only sets after the run ends. A flag from the first run of a
   task gets no task; later runs get the previous run's chat.
4. **Onboarding talks like a developer tool.** It shows "per 1M tokens" pricing and old models
   (gpt-4o-mini and similar). Connectors mention "MCP server". The target user knows none of these
   words.
5. **No frontend tests.** `store.ts` is 3,241 lines and has none. The two sidebar bugs above
   would have been caught by one test of the `chat` event. The Rust side has 317.
6. **Two design systems that disagree.** `design.md` says 13px body; `docs/DESIGN.md` says 16px
   and describes the user as "Developer working…". About 700 hard-coded font sizes in the app,
   mostly 10–13px. This is the real cause of "I have to zoom in".
7. **Repo weight.** A 23MB Linux backend binary (`app/src-tauri/binaries/zwork-backend-x86_64-unknown-linux-gnu`)
   and a 14MB video (`video/launch/deliver/zwork-intro.mp4`) are committed. Every clone pays for
   them forever. Release assets belong on the GitHub release; video in LFS or out of the repo.
8. **Surface sprawl.** `site`, `landing`, `landing-legacy`, `minimal-chat`, `admin-web`, plus 30+
   docs, several of them stale (`PRODUCT.md` still has the technical-user framing that
   `POSITIONING.md` replaced). The admin page is lazy-loaded inside the desktop app.
9. **Large files.** `server.rs` 2,978 lines, `harness_turn.rs` 2,768, `Settings.tsx` 2,140.
   Not urgent on their own, but they are where the bugs above came from.

## 3. Push-back

1. **Fix the type scale, don't zoom.** 110% zoom makes everything bigger, including chrome that
   was fine. The right fix is one decision in `design.md`: body text 14–15px, secondary 13px,
   nothing under 12px, then replace the hard-coded sizes with tokens. Delete `docs/DESIGN.md` or
   merge it, so there is one source.
2. **Students.** `POSITIONING.md` rejected students as the lead, for good reasons: ChatGPT is
   free or $8 for them, their work is chat-shaped, and they leave every semester. Nothing in this
   review changes that. The student workflows below are where zWork is *fine*, not where it
   *wins*. If students become the target, rewrite the positioning doc first, not the app.
3. **Stop copying features.** "Our implementations of other AIs' features are bad" is mostly
   because they are copies of features built for a different product. Inbox, projects and search
   exist in ChatGPT and Claude to organise *chats*. In zWork the unit is the *recurring job*. Build
   the job's screens well and let the chat features stay plain.

Star counts and claims come from these roundups, not from checking the repos.

**What all of them miss:** none of them is built around a recurring job with a result you open
in Excel or Word. They are chat apps that can also do things. zWork's scheduler, inbox and
approve-before-send are the actual difference, and they are the least polished part of the app.

### What to take from ZCode's reading experience

I did not clone or run ZCode; this is from reviews and its screenshots. The pieces that make it
easier to read and that zWork can adopt without copying its layout:

- Body text at a normal reading size, with the app chrome smaller around it. zWork does the
  opposite: everything is equally small.
- Few things in the top bar. ZCode's controls live in panels, not floating icons.
- One accent colour used for one thing (the agent's current step). zWork's step rows,
  badges and buttons all compete.

## 5. Workflows: zWork vs Claude vs ChatGPT vs open-source

"Steps" means what the user does, not what the AI does. Closed-product capabilities come from
`POSITIONING.md` and [techsy.io](https://techsy.io/en/blog/claude-cowork-vs-chatgpt-agents) /
[lowcode.agency](https://www.lowcode.agency/blog/claude-cowork-review); check current plans before
quoting them publicly.

### Professionals (the wedge)

| Job | ChatGPT ($20 Plus) | Claude Cowork ($20 Pro) | OpenWork / Eigent (free, own key) | zWork ($12, or free with own key) |
|---|---|---|---|---|
| Monthly expense report from a bank export into the accountant's Excel template | Upload CSV and template each month; get a file back from the cloud sandbox. No scheduled file access. | Point at the folder; works in place; can schedule while the app is open. | Works in place; you set up the model and tools first. | Point at the folder once, schedule it monthly, result lands in Inbox with the `.xlsx`. |
| Weekly client update from inbox + tracker | Agent in the cloud browser; you log in to each site inside it. | Microsoft 365 hooks; strong if you live in Outlook. | Needs an email connector you configure. | Gmail/Notion via connectors, scheduled, asks before sending. Connector setup must not say "MCP". |
| Chase unpaid invoices | Draft only; you send. | Drafts, can send with approval. | Depends on setup. | Drafts, waits for approval in Inbox, then sends. This is the cleanest fit for the inbox. |
| Read a folder of PDF invoices into one sheet | Upload limits per message. | In place. | In place. | In place, no limits, repeatable. |

**Where zWork wins:** price, any model, the job repeats without you, every send waits for you.
**Where it loses:** brand trust, Microsoft 365 depth (Cowork), polish, mobile. The inbox is the
product's proof of work and today it is the weakest screen.

### Students (fine, not a win)

| Job | ChatGPT (free / $8 Go) | Claude | Open-source | zWork |
|---|---|---|---|---|
| Understand a lecture or a reading | Study Mode asks questions back instead of answering ([eWeek](https://www.eweek.com/de/news/openai-chatgpt-study-mode/)). | Learning mode. | None built in. | Plain chat. No learning mode. Loses. |
| Turn a week's PDFs into study notes | Upload each time. | Works on a folder. | Works on a folder. | Works on a folder; can repeat weekly. Small edge. |
| Deadline digest from course emails | Tasks can run but can't read local files. | Scheduled, if the app is open. | Manual. | Scheduled, lands in Inbox. Real edge, but one job. |
| Write an essay | Chat. | Chat. | Chat. | Chat. Parity at best. |

A student would pick ChatGPT because it is free, on their phone, and has Study Mode. zWork's one
student job is the scheduled digest, which is the professional wedge in different clothes.

## 6. Inbox: what it should be

The small fixes in section 1 made it less wrong. The design is still a list of chat
notifications. For a product whose main feature is recurring jobs, the inbox should be the
**results of jobs**:

- **Group by task, not by time.** One row per scheduled task: its last result, when it ran, and
  whether it needs you. History behind the row.
- **Three states only, as the first thing you see:** *Needs your OK* (drafts waiting to send),
  *Done* (result plus the file it produced, openable in Excel/Word), *Didn't work* (plain reason,
  next try time, "Try now").
- **The file is the result.** A finished expense report shows the `.xlsx` with an Open button,
  not a paragraph about it.
- **Approve in place.** An email draft shows its recipient and text with Send / Edit / Don't send.
  No jumping into the conversation to approve.
- **The conversation is the log**, one link away, for people who want to check what it did.

This is roughly a week of frontend work on top of the existing store; no backend change except
fixing the task id lookup (2.3).
